# AGENTS.md — voxel

## What this is

A browser-first, voxel-first 3D graphics and rendering toolkit for the owner's strategy and building games — voxel chunks, low-poly procedural geometry, imported assets, instanced entities, overlays, effects, and orthographic or perspective views. Stack: strict TypeScript, a Three.js WebGL2 runtime, Vitest + Playwright.

Non-goals: not a simulation engine, ECS, game-rules library, UI framework, persistence layer, asset-evolution studio, or a general-purpose Three.js replacement. A useful renderer shared by two games beats a universal abstraction that serves none well. AoE2 is the standalone sole-renderer host; City is the embedded borrowed-renderer lane; Townscaper adoption and imported-asset/extension APIs remain future work. **Do not claim a package, command, backend, benchmark, shader, mesher, adapter, or test exists until live files and executable behavior prove it.**

These non-goals describe the public renderer/runtime boundary. Private Studio authoring storage and explicit consumer fixtures may live in this repository, but renderer/core never owns durable consumer data or authoritative simulation.

Voxel's own rules — its strengthenings of the fleet constitution and the rules it adds — live in [docs/policies/local-rules.md](docs/policies/local-rules.md). They bind alongside the constitution below and win where they overlap. Do not write them into that section: it is a verbatim copy of `loop-ops/FLEET.md` and `/sync-instructions` rewrites it wholesale, which silently deleted every one of them on 2026-08-01.

## Fleet constitution

- Work headlessly by default; go non-headless only when nothing else can complete or verify the task, and say why.
- These rules are strong defaults, not law: when one would make the work worse, deviate and say why.
- Scale the approach to the task: trivial changes directly; substantial work as explore → plan → implement → verify, with subagents when work is genuinely parallel.
- When two attempts at the same problem have failed, stop iterating alone: build the fixed benchmark or reproduction that settles the question, fan out independent subagents on deliberately different approaches against it, then switch role to evaluator — score their output yourself rather than trusting their reports, and take the best. A third pass at the approach that already failed twice is the expensive mistake. (Established 2026-07-31.)
- A model call is a legitimate component of a program here, not only an authoring aid: this fleet has one user, with Claude Code and Codex subscriptions, so a pipeline may call a model at runtime — vision included — wherever that beats a hand-written heuristic. The repo's trust boundaries are unchanged and are what make it safe: model output proposes, a deterministic check disposes, and it never self-certifies. Reaching for a brittle heuristic to avoid a model call is the mistake, not the other way round. (Established 2026-07-31, after a geometric stud-pitch reader answered 4 of 50 booklet regions and a headless vision call answered 6 of 6.)
- Toolchain baseline: develop and run gates on Node 24, which every Node repo pins in its own `.nvmrc`. A repo that must keep supporting an older major says so in its Gates section and keeps a CI job proving it, because otherwise an agent on the wrong version reads a version failure as a code failure and starts debugging the repo. (Established 2026-07-31, after `node:check` failed on Node 22 and looked like a broken checkout.)
- Delivery boundary: each minimal coherent verified unit is reviewed, staged (scoped files only), and committed promptly — never commit failing or partial work as a checkpoint. Commit to `main`; push at the end of every task.
- Concurrent sessions share one worktree and one index: commit by explicit pathspec (`git commit -- <files>`), never `git commit -a`, `git add -A`, or `git add .` — a sweeping commit captures whatever another session has staged. (Evidence: voxel c024b33, 2026-07-17.)
- The repo's gates must pass before every commit that touches code; doc-only changes need a self-reviewed diff.
- Review: self-review trivial changes; adversarially review non-trivial ones — independent agents that try to refute the change against the live code. High-risk work (persistence/migrations, security/auth, concurrency, money, supply chain, edits that reach sibling repos) escalates to the multi-cli-review skill. Reviewers must read the live code; verify reviewer claims against the codebase before acting on them; substantive findings outweigh approval votes.
- Dependency changes: re-resolve the lockfile, run the repo's audit gate (a new HIGH/CRITICAL is a blocker), and note the audit result in the commit message.
- Docs are part of the change: update every affected surface in the same commit; write prose one line per paragraph (no hard wrapping); never reference or mandate files that don't exist.
- Bias to continue: work through the whole accepted plan without mid-plan check-ins; context management is the harness's job, never a reason to stop. Stop only for a genuine blocker, a direction-changing decision, or an explicit stop. (Established 2026-05-01; reinforced 2026-07-05.)
- Error messages are a product surface, and coverage of them is a standing requirement rather than something done when a message happens to be touched: every path that rejects, fails, or throws says what happened, which specific input caused it, and what would satisfy it — never a bare `Validation failed`, `invalid input`, or a silent boolean false. A diagnostic that forces a human or an agent to read the source to learn why is itself a defect; fix the message in the same change as the bug. Where a failure has known causes and known non-fixes, the message says which — an agent that reads "increase coverage" will raise a number that has already been measured not to work, so name the lever and name the dead end. Treat a repo's error paths as a surface to audit, not a place to react. Applies equally to validators, CLI output, and assertion text. (Established 2026-07-18, after city's `placeService` answered five rejected placements with only "Validation failed"; widened to coverage 2026-08-01, after voxel's Riverfall surface told three sessions in a row to "increase particle coverage" when particle count was the one thing measured not to fix it.)
- Steering compounds: when the user gives a direction that generalizes past the immediate task, land it in the canon in that same session — here if it is fleet-wide, else the repo's AGENTS.md or lessons file — so the next run inherits it instead of relearning it, and say what was captured and where. (Established 2026-07-18.)
- Closing report: when a task is done, report it in plain language — what the problem was, what was tried, what the hypothesis was, what worked, what did not, and what comes next. The attempts that failed belong in it; they are the part the next session would otherwise pay to rediscover. Disclose progressively: lead with the outcome and the number behind it, keep the supporting detail one question away, and treat jargon and implementation detail as something the reader asks for rather than the default — a report that opens with the mechanism makes the reader do the summarising. End with the open questions whose answer is genuinely the owner's: a call about direction, priority, or a trade-off nobody else can settle. Anything the code, the measurements, or a sensible default already answers is not a question — decide it, say what was decided, and carry on to the next step. (Established 2026-08-01.)
- Reviewer model pins live only in `../loop-ops/docs/skills/multi-cli-review.md`, and loop-work model directives in `../loop-ops/DIRECTIVES.md` — never hardcode model IDs anywhere else.
- Lessons files (`docs/learning/lessons.md` where present) require evidence anchors — source, fix commit, test id, behavior delta; unanchored lessons are folklore.
- Recursive loop: before running or driving a pass, read `../loop-ops/docs/skills/recursive-playtest.md`; before building loop machinery, read `../loop-ops/docs/skills/building-recursive-loop.md`.

## Gates

Authoritative commands live in `package.json`. For non-trivial work, run the smallest relevant checks while iterating, obtain adversarial review, fix its findings, then run one final **`npm run verify`** (build · test · typecheck · lint · compatibility · public-API · core-only / mesh-worker / three package checks · supply-chain · browser) before declaring implementation complete. Any later code change requires another full `npm run verify`; a later doc-only change requires the applicable doc checks. Doc-only work must at least pass diff review, link/path checks, Markdown-fence and whitespace checks, and literal intent/forbidden-content searches for user-steered wording; consolidate one coherent doc-only correction before pushing. Never invent a successful command result.

Renderer changes verify to the risk: deterministic unit/property tests (storage, meshing, bounds, seams, revisions, picking); browser tests against the served app (resize, input, capture, context loss, teardown); fixed camera/viewport/DPR reference scenes with before/after screenshots; structured render metrics (draw calls, triangles, GPU resource counts, dropped stale jobs); repeated rebuild/teardown showing stable resource counts; measured performance on named scenes with hardware/browser recorded.

Visual work is never complete until the rendered result has been visually inspected at the intended camera, viewport, and device scale, plus at least one adversarial angle or state appropriate to the risk. Automated pixel comparisons preserve known output but do not replace first-hand inspection; record what was inspected and fix visible discrepancies before declaring completion. (Established 2026-07-26.)

## Invariants & boundaries

- The game simulation is authoritative; renderer state, scenes, meshes, materials, textures, acceleration structures, captures, and metrics are disposable derived artifacts.
- Public render inputs are bounded, structured-clone-safe data — opaque never-reused render keys or explicit local-ID generations, plus schema/epoch/revision — with no callbacks, DOM objects, Three.js objects, or consumer world types.
- Portable core, voxel storage, meshing, and voxel/heightfield ray-query code must not import Three.js or touch the DOM. The Three.js adapter owns all GPU and browser integration (`THREE.Raycaster` included).
- Consumer adapters translate game snapshots/deltas into engine inputs; roads, zones, AoE units, Townscaper facades, and production simulation components stay in their game repositories. Bounded explicit consumer fixtures may live here as evidence, but never become renderer/core authority.
- Promote scene-enabling mechanisms into Voxel only as bounded, game-neutral capabilities reusable by downstream games; keep each scene's choreography, scripted trajectories, physics or simulation, causal event rules, and game semantics in Studio or consumer fixtures or game-owned adapters, with the renderer observing versioned plain-data state it is handed each frame.
- Scenes simulate live (owner rule, 2026-07-30): every scene computes its motion in real time, at frame rate, in the browser. This is the whole point of having scenes — they exist to exercise the runtime a real-time game will actually use, and a scene that replays baked poses tests the decoder instead. A pre-recorded trace is never a scene's source of truth; it is at most a determinism fixture a test compares against, and it must never be what the studio plays back for the owner. Scenes still recorded when this rule landed — Machine Works, Riverfall, Windmill, and the chain's replay lane (the chain alone already has a live profile beside it) — are delivery work to convert, not optional cleanup, and no new scene may be added on the recorded lane. Judge a live scene by what the renderer sustains: frame budget, draw calls, and resource counts under real simulation, inspected on screen rather than measured from a file.
- Everything solves at 60 Hz (owner rule, 2026-07-31): one lane constant, `LIVE_TIMESTEP_SECONDS_V1`, and every solver lane derives its step from it rather than spelling a literal. 240 Hz was the owner's monitor refresh rate, never a target — no consumer runs that high, and a rate nobody ships is a rate nothing is really tested at. A lane that cannot yet meet it says so where its constant is declared, with the measurement that blocks it, and is delivery work rather than a permanent exception. `tests/studio/solver-rate.test.ts` fails on any lane that drifts off the shared constant.
- Coordinate, unit, color-space, alpha, and transform conventions are explicit at the boundary — never an implicit axis swap, scale, or color conversion.
- Input typed arrays are borrowed and copied on ordinary ingest; only an explicitly named ownership-taking API detaches adapter-owned transfer buffers, and simulation-owned memory is never transferred.
- Meshing is deterministic for identical canonical inputs; async jobs carry world epoch, resource incarnation, source revision, and dependency revisions so stale worker results never overwrite newer state.
- Accepted state is tracked separately from presented state: mesh swaps at frame boundaries, picking reads the same presented data as the canvas, capture waits for or reports incomplete presentation. Committed `pickPresented` requires a world whose descriptor carries `chunkProfile` and whose runtime enables `voxelWorkers`; other paths report typed unavailable outcomes (`no-presented-frame`, lost/restoring/failed/disposed).
- GPU ownership is explicit — every renderer, control, listener, frame callback, geometry, material, texture, render target, cache entry, extension scope, and worker has an idempotent disposal path; context loss/restore follows an explicit state machine.
- Time is injected through the frame context; deterministic paths never read `Date.now()`/`performance.now()` directly (tests drive a manual clock).
- Physics flaws are fixed as universal law (owner rule, 2026-07-31): when a simulation behaves impossibly, the repair is a law of this voxel universe, never a patch to the scene that exposed it. State each law as what holds, not what is banned: surfaces resist sliding, rolling contact resists the roll, a bearing resists its shaft, air resists both travel and spin, a collision returns less than it receives, a passive machine only ever spends the energy it started with, and Newton's three laws hold and are measured rather than assumed. Laws live in one module, published as `voxel/physics`, and are applied where rigid bodies are created — every solver lane in this repository, the consumer fixtures included — so no scene here can opt out by forgetting to opt in. A downstream game keeps its own solver and does not inherit them automatically; it borrows them by calling `applyPhysicsLawsToBodyV1` at its own body-creation site, which is the whole reason the module ships free of Three.js, Rapier, and the DOM. Content may tune a law per material and must state the measured effect; content may never exempt itself, and a law that a body can escape by declaring nothing is not a law. Prove each with a counter-run that fails when the law is overridden away, and prove no content escapes with a test that walks every material and every body. When a new law shortens a throw or moves a landing point, move the scenery to follow the physics — bending a machine to protect a number is how a workaround becomes furniture. Retire the scenery that existed only to compensate for the missing law.
- Placed things are solid (owner rule, 2026-07-30): no two placements may co-exist in the same space — recorded poses included — and no two same-facing surfaces may lie on one rendered plane, because coincident same-facing area is what fights for visibility and always means shared volume. Flush back-to-back contact is the only legal coincidence; recorded physics may dent a contact only by its numerical slop; where two grains must nearly meet, keep them apart by an authored clearance off every involved lattice (the Machine Works still-settle is the pattern). Enforce at content boundaries — `sceneOverlapsV1`, `sceneSurfaceFightsV1`, the studio's live conflict line, and the fixtures' generation-time penetration budgets — and fix geometry at its source; never hide a fight with renderer depth tricks.
- Never create one scene object or draw call per voxel at production scale — cull hidden faces, mesh by chunk/region, instance repeats, and make overflow policy explicit.
- Keep `three` an optional peer (`peerDependenciesMeta`), externalized from the build, aligned to one tested release, and deduped for linked Vite consumers — verify a single runtime Three.js instance. WebGL2 via Three.js `WebGLRenderer` is the first production backend; keep the data plane portable but build no speculative backend abstraction before a measured need.
- Public API compatibility holds unless the task authorizes a versioned breaking change; schema changes require explicit versioning and migration guidance. Files stay normally under 500 lines, and no new hand-authored file may exceed 1000. Treat existing files above 500 lines as ratchets: do not materially grow them without an explicit reason and a bounded extraction plan recorded with the change.
- Do not modify a sibling repo (`../city`, `../townscaper`, `../aoe2`) unless the task explicitly includes it — consumer code is evidence for a contract, not code that belongs here.

## Known traps

- Do not approve visual behavior from source inspection alone, structural correctness from a pleasing screenshot alone, or performance from a single unrepeatable frame-time number — the three classic renderer false-positives. (The concurrent-index commit trap that bit this repo — c024b33, 2026-07-17 — is now in the constitution above.)
- Whole-app gates are unattributable in a shared worktree. `npm run test:browser` serves whatever is on disk, so a concurrent session's half-written studio code fails specs that have nothing to do with your diff — the 2026-07-30 full review saw four such failures, including a `.scene-canvas` that never became visible. Never read those as your own result and never blame the other session without proof: add a throwaway `git worktree` at HEAD, apply only your own staged diff, `npm ci` there, and run the gate in that tree (the same review then went green through the specs that had failed). The same reasoning covers any gate that exercises the whole app rather than your files.
- A green test proves less than it looks when a timestep changes underneath it. Moving the live lane from 240 Hz to 60 Hz exposed that a committed Machine Works change had passed for the wrong reason: the carrier's tip was never implemented, and at 240 Hz the product left the carrier by an accident of contact timing. Anything whose result depends on contact resolution should be run at more than one rate before it is believed. (2026-07-31, commit 73f9bbc.)
- A test that builds its own world tests its own world. A Machine Works run test constructed bodies from the scene's authored placements while the studio builds them from the live profile's opening poses, so it passed for weeks against a world the studio never builds. Construct through the same path the product uses, or the test is fiction. (2026-07-31.)
- Numbers stay sane while the picture goes wrong, and the picture lies too. The mill's flour rose one step per blow forever and climbed out through the roof with 953 tests green — only the render showed it. In the same scene, what looked like a sack sitting on the roof was the far sail seen against the roofline (sails top out at 2.625, roof reaches 3.25); a side elevation settled it. Look at the render, then measure before "fixing" what you saw.
- A mechanism's contacts are declared, not discovered. The windmill jammed in its own bearing, then flung its hammer over the top, until the profile named exactly which body pairs may touch (`contactPolicy`). Everything-meets-everything is right for a chain or a heap and wrong for a machine — a shaft has to pass through the housing that holds it. (2026-07-31, commit be30dd8.)
- A test written against a fixed reviewer claim can pass for the wrong reason. Neutralize the fix and watch the test fail before believing either. The 2026-07-30 review discarded two tests that passed with and without their fix — one because an unrelated guard rejected the payload first, one because the validator already caught what the estimator had missed — and only the failing-first check separated a real repair from a plausible story.
- A gate can point the wrong way after the rate moves, and a per-second name does not make a quantity rate-independent. The windmill's shaft-axis direction rate is a per-step angular response divided by the step, so at 60 Hz its 0.05 rad/s ceiling passed only the candidates whose hammer flew over the top and never struck, and failed all sixteen that ran a clean cycle. When a threshold starts rejecting the outcome it exists to protect, re-derive it from what it defends rather than widening it. (2026-08-01; see the lessons file for the 1,100× measurement that separated the blow from the wobble.) The check that catches this is `tools/studio/solver-rate.test.ts`, which now allows no rate literal anywhere in the repository.

## Conventions

- Session start: read `README.md`, `docs/design/spec.md`, and `docs/learning/lessons.md` before substantial work — the lessons file records what was already tried and cost someone a day, and until 2026-07-31 nothing told anyone to open it, which made it write-only; inspect the relevant consumer path in `../city`, `../townscaper`, or `../aoe2` before changing a public contract intended for it.
- Keep `README.md` truthful about implemented status and `docs/design/spec.md` aligned with architectural contracts and delivery gates; update consumer integration notes when a public API or supported Three.js range changes. Add heavier devlog/decision/progress docs only when recurring work makes them useful.
- Keep `README.md` capability-oriented: do not add Studio scene descriptions, inventories, status, provenance, metrics, or per-scene links there.
- Record why an authored decision exists as typed graph edges, not prose: a `beneficiary` sentence cannot be traversed, so nothing can check that a chain of reasons terminates or that a stated need is served. Project a system's purpose ledger onto [the purpose graph](docs/design/purpose-graph.md) and let the kernel find orphans, justification cycles, unserved needs, and contradicted system boundaries. Keep the ledger prose as the single source of truth and add only edges and evidence. (Established 2026-07-28, after translating Windmill's prose exposed two mutually justifying contact pairs.)
- Creative model/recipe work is judged by contrast coverage, not item count: palette or seed swaps alone do not count as distinct; a promoted model must differ from its nearest catalog neighbors on at least two independent axes among topology/negative space, multi-view silhouette/massing, scale/proportion, construction/part grammar, material rhythm, or supported motion. Generate deterministic contrast batches, inspect fixed multi-view contact sheets plus structural fingerprints, reject near-duplicates, and extract a reusable part only after a second real use; keep consumer-specific art in its game repository and do not turn Voxel into an asset-evolution system. (Established 2026-07-26.)
- Record source, version, license, and redistribution requirements for imported code, shaders, textures, models, and sample assets — permission to view a sibling asset does not make it appropriate for a reusable package.
- Temporary captures, traces, benchmark output, and renderer dumps belong in ignored output directories; commit only durable fixtures, concise evidence, and documentation useful to a future maintainer.
