# Defect register

Every defect the owner reported, with the symptom as they saw it, what the investigation found, the root cause, and the check that covers it from now on.

Unlike a lesson, an entry stays after it becomes a gate. This is the standing list of what the gates could not see, which is where the next defect comes from — so it is read for its pattern, not only for its instances.

## 2026-09-01 — Root cutaway fitted the crown and reduced its subject to tiny traces

**Symptom, as seen in visual review.** The root cutaway still framed the entire aboveground tree, so the accepted roots occupied only a tiny part of the canvas and the belowground inspection mode did not actually inspect its named subject.

**What the investigation found.** Cutaway camera fitting admitted every accepted plant organ and then imposed a minimum height of the full tree diagnostics plus `0.14 m`. The separate cutaway azimuth kept the aggregate fine-root direction from collapsing completely, and the material contrast made a few pixels detectable, but neither mechanism gave the roots useful screen area. The mature accepted cutaway actually contains `196` root voxels, yet the camera distance was governed by crown height rather than those exact instances.

**Root cause.** The camera fitter treated render visibility and focus geometry as the same set. Root cutaway correctly kept the whole accepted render frame, but its presentation-only camera had no derived belowground subject selector, so a view intended for root inspection inherited the ordinary whole-tree envelope.

**Outcome.** Root cutaway now derives its focus geometry from every exact vertex of every accepted root-batch voxel. It walks only the accepted shared face-neighbour lattice into the root-connected seed/bud body and, once basal wood exists, stops two cell layers beyond the first reachable wood voxel. Before root emergence, when that accepted batch is truthfully empty, the exact accepted seed/bud batch alone supplies the focus and both root-shaft witnesses remain null; after root emergence but before wood, the connected seed body supplies basal context without requiring absent wood. The renderer still receives and draws the unchanged complete accepted frame; no root is invented, no upper organ is hidden and no simulation value changes. Ordinary hero, side and overhead fitting still uses the prior full aboveground-and-litter subject. At the mature `1280 × 720` HUD-reserved unit fixture, the coarse and aggregate fine-root authority shafts now span `166.29 px` and `227.02 px` respectively.

**How it is checked from now on.** `oak-browser-camera.test.ts` independently transforms the accepted root batch and requires the focus selector to include that exact ordered vertex population, reports the exact root voxel count, includes some but not all accepted seed/bud-plus-wood context, and keeps that context below `20 mm` at the gated early-growth state. A mature HUD-reserved camera gate requires both root shafts above `120 px`, the selected bounds clear of the HUD and every frame edge, and the exact accepted root count; a day-3 counter-run requires the radicle cutaway to remain valid with zero accepted wood. Separate day-0 and day-2 regressions require zero fitted root voxels, null shaft evidence and a fitted vertex count equal to every and only accepted seed/bud voxel. The real-browser cutaway pixel and fixed-view gates remain responsible for the rendered composition and material contrast after baseline refresh.

## 2026-08-31 — The oak exposed renderer counts but not whether frames were arriving slowly

**Symptom, as reported.** “Rendering feels slow. Show FPS somewhere on the info panel.”

**What the investigation found.** The HUD reported presented revision and GPU resource counts, and the browser host mapped `requestAnimationFrame` timestamps into the fixed-step simulation clock, but no visible value described the cadence at which successful canvas frames were actually presented. The available `60 Hz` simulation step and cumulative runtime frame count could both produce a plausible but false FPS number because neither measures recent wall-clock presentation cadence.

**Root cause.** Renderer diagnostics were treated as inventory and revision evidence only. The case study had no bounded presentation-timing instrument, so a viewer could perceive slowness but could not distinguish a slow display loop from accelerated biological time, a paused simulation or remembered target-rate documentation.

**Outcome.** A compact above-fold `Render frame rate` row now observes every foreground RAF-driven `runtime.frame` attempt and counts a frame only when that call returns a presented manifest. It publishes a one-decimal recent cadence after a half-second warm-up, updates at most four times per second, retains a missed-frame interval so a visible stall is not smoothed away, decays to `0.0 FPS` across repeated unavailable frames, continues while biological time is paused, excludes manual command, resize, camera and test-harness renders, and resets across hidden-tab transitions. The readout is volatile display telemetry: it is not simulation authority, GPU completion time, compositor scanout or a hardware-independent performance promise. Isolated day-100 CPU frame construction remains slower than the `16.67 ms` 60 Hz work budget before submission or GPU work, so the visible FPS instrument does not imply that target has been met.

**How it is checked from now on.** A deterministic sampler gate drives synthetic `30`, `60`, `120` and `240 Hz` presented timestamps, requires warm-up before publication, observes a missed-frame reduction, expires a healthy value after repeated unavailable attempts, proves recovery and later-window eviction, rejects exact duplicate or reversed time, verifies hidden-tab reset plus listener disposal, and checks that the host glue ignores manual timestamps while preserving undefined runtime results as failures. A real-browser control starts a `30 Hz` RAF timestamp stream, pauses biology, switches that stream to `20 Hz` and requires convergence to exactly `20.0 FPS`, so neither the fixed `60 Hz` simulation target nor a pre-pause cached value can pass as telemetry. The ordinary mount gate separately requires the above-fold value to leave `measuring…`, carry a positive numeric `FPS` unit and remain separate from the simulation evidence contract; it deliberately sets no machine-dependent minimum. ## 2026-08-28 — `main` had not seen a green CI run in five weeks

**Symptom, as reported.** "Fix github CI", followed by: "You need to proactively monitor these things instead of hearing about it from me."

**What the investigation found.** The last successful CI run on `main` was on **2026-07-24**. Every push since — **131 runs, 100 failures and 31 cancelled, no successes** — was red.

The streak is not one defect. It spans a workflow matrix change (the jobs were `Node 22 complete` in early August and are `Node 24 complete` now) and at least one unrelated cause: 2026-08-08 also failed `npm audit`. What was diagnosed here is the state of the streak's most recent five runs, 2026-08-18 through 2026-08-28. The earlier failures were not investigated individually and should not be assumed to share this cause.

Those five do **not** fail identically, which a first pass recorded that they did after reading the two most recent. Pulling all five Windows logs found two more timeouts that appear in some runs and not others, on tests that passed in the run everything else was measured from.

Only the newest of them failed in every job, on a TypeScript error that landed in `39a4d75`; the other four had both `Node 22 portable` jobs green and failed only in `Node 24 complete` — the one job that runs `npm run verify` end to end, and therefore the only one that runs the browser suite. It failed on Linux and on Windows alike.

Eight separate defects, not one. Two of them were found only by pulling all five runs' Windows logs rather than the two most recent — which is how "they fail identically" survived a first reading — and the eighth only by pushing the fix and reading the run it produced:

1. `playground-joint-overlay.test.ts:86` handed a `LiveBodySnapshotV1` to `playgroundPrismaticCoordinateV1`, which declared `PlaygroundBodySnapshotV1`. The function reads only translation and rotation, and its own file comment says its checks "hold identically over either lane's frames" — the type said otherwise. Landed in `39a4d75` and never typechecked locally before the push.
2. `model-studio-chain.spec.ts` settled the live world to an absolute tick 30 without pausing it first. A live scene free-runs on the wall clock from the moment its solver is ready, so the tick it has reached when the test arrives is a measure of how slow the machine is. CI arrived at 54. Machine Works and the windmill already open with `setSceneAnimation(false)`, which builds the world paused; the chain never adopted it.
3. `model-studio-lighting-preference.spec.ts:280` asserted that the scene clock advanced under 200 ms across a resume. What it actually measured was its own round trip to the page. CI measured 541.9 ms on a player that was behaving correctly, and the invariant it was reaching for — that resuming does not credit the pause — is already proved exactly against an injected clock in `player.test.ts`.
4. `model-studio-machine-works.spec.ts:612` exceeded the 60-second test budget. The 71.3 s (Windows) and 68.5 s (Linux) in the logs are not its cost — the test was killed at sixty and those include unwinding and writing a failure trace. Measured alone on the workstation it is **53.0 s**, so it had been running at 88% of its budget locally all along. It now declares `test.setTimeout(180_000)` at its own site, the same budget `windmill-assets:279` already took for the same reason.
5. `model-studio-lighting.spec.ts:724` exceeded the 60-second budget on Windows in two of the five runs, and passed at 50.4 s in a third. Uses the suite default.
6. `model-studio-scene-annotations.spec.ts:639` exceeded it on Windows in one run, at the `expect.poll` on line 914, and passed at 54.2 s in another. Uses the suite default. Note that raising the assertion budget does **not** bound this one: the poll callback hung in flight, and `expect.poll` cannot interrupt a callback it is already inside, so it runs to the test timeout whatever the matcher is allowed.
7. `model-studio-riverfall.spec.ts`, the `model-studio-riverfall-overhead.png` capture in "Riverfall solves its water in the browser and plays back nothing" (`:445` when it failed, and it has moved twice since — name the assertion, not the line), could not capture a screenshot inside Playwright's unstated 5-second assertion default. Review proposed a better-sounding cause — that the canvas never goes still, because `settleTo` pauses the solver and not the scene transport — and it was tested and disproved: stopping the transport moves 3,786 pixels, because the studio then stops applying the live presentation's poses and all 96 foam flecks snap back from the plunge pool to their authored lattice. The river's foam is placed by the running frame loop. The canvas is otherwise static after a settle, and the failure was slowness. It declares its own `test.setTimeout(180_000)` now, from **86.5 s measured on windows-latest**.
8. Found only by pushing the fix and reading the run: the Windows runner answers a navigation with **`net::ERR_NO_BUFFER_SPACE`** — the operating system out of socket buffers — at an arbitrary point in the suite. On the first run after the fix it hit test 41 of 116 while the other 115 passed. Twenty-three spec files each start their own Vite dev server and pull a module graph through it, which is where the sockets go. Mitigated with `retries: 1`, which does not hide a broken test (every defect above fails twice) and which Playwright reports as *flaky* rather than as passed. **The durable fix — one shared dev server for the run instead of twenty-three — is not done.**

**Root cause.** Two, and only the first is about tests.

The gate that ran before each of these pushes was not the gate that runs on CI. Locally the browser suite passes because the machine is several times faster than a shared runner rasterising in software; nothing on the author's machine can exercise a slower one. Both CI legs failed, so this was never "the Windows half" — it is every machine that is not this one. That made each of these a defect only CI could see, on a lane nobody was reading.

Underneath that, the browser lane had no timeout discipline. `tests/testing/test-timeout.ts` derives every vitest budget from measured work — a rule this repo bought on 2026-08-07 after fifteen tests expired on a documentation-only diff — and `test-timeout.test.ts` scans for any test that opts itself below the allowance. That scan deliberately skips `tests/browser/**`, on the stated grounds that Playwright specs have "their own gate and their own timeout config". They had neither: a flat 60,000 ms that no measurement stood behind, and Playwright's 5,000 ms assertion default, which is precisely the unstated-default-below-the-allowance shape the 2026-08-07 entry describes.

**What the first fixed run showed.** `Node 22 portable` green on both operating systems, `Audit and package` green, and **`Node 24 complete` green on Linux for the first time since 2026-07-24**. Windows: 115 passed, one failed, and the one was defect 8 above rather than anything diagnosed here. The four browser tests that had been failing all passed, with margins the reporter printed: `machine-works:612` at 41% of its budget, `riverfall` at 72%, `scene-annotations:639` at 55%.

That 72% is why the budgets moved again afterwards. Three points under the gate is not headroom, and the number that produced it — a workstation measurement — was the wrong one to have used. Every budget is now taken from the Windows leg.

**Outcome.** Run 33205964399, 2026-08-28: **all five jobs green** — the first fully green CI run on `main` since 2026-07-24. Windows: 116 passed, none failed, **none flaky**, 15.7 minutes; the socket exhaustion did not recur, so the retry that covers it was not spent. The margins the reporter printed, all comfortably inside: `lighting-preference:49` at 65% of its budget, `riverfall:247` at 46%, `scene-annotations:639` at 41%, `windmill:129` at 38%.

`lighting-preference:49` at 65% is now the closest to the edge and the one to watch; on the previous run it was not in the top five at all, which is the kind of movement the reporter exists to make visible.

**How it is checked from now on.**

- `tests/testing/browser-timeout-headroom.ts` is a Playwright reporter that fails a *passing* run when any test has spent more than 75% of its budget, and prints the five closest to the edge on every run.

  This is the class check rather than the instance check, and measuring it settled where the defect actually lived. `machine-works:612` takes **53.0 s on the workstation, of the 60 s the lane gave every test** — 88%, on the author's own machine, with nothing counting. It was never a fast test a slow runner broke; it was a test with seven seconds of room, and any host slower than this one was going to spend them. Had this reporter existed, the local run before the first red push would have said so. That is the point: the margin is visible where the failure is not.
  The reporter was confirmed to bite before it was trusted: with its threshold neutralized to 0.0001, a run reporting "2 passed" exited 1.
- Budgets are sized for the test they guard, and every one is measured on **windows-latest**, the slowest leg. The default is **110,500 ms** — the slowest test that actually uses it (`scene-annotations:639` at 65.5 s) plus `test-timeout.ts`'s 45-second allowance for a machine that is not the author's. The three heavy tests carry their own `test.setTimeout(180_000)` with their own measurement beside it: `windmill-assets:279` already did, and `machine-works:612` (53.0 s here, 72.9 s there) and `riverfall:247` (86.5 s there) now do.

  Two earlier attempts at this number are worth remembering, because both were arithmetic on the wrong measurement rather than mistakes of judgement. The first fed a CI figure into `timeoutForMeasuredWorkMs`, whose four-times multiple exists to scale a *workstation* number — 285,000 ms, under which nothing could ever reach the margin gate. The second took the workstation figure instead and produced a default that three Windows tests were already close to. A default stretched to fit the heaviest member is a budget for nothing else; a default taken from the fastest machine is a budget for nobody.

  There is deliberately no `process.env.CI` branch anywhere: a budget only CI executes is another instance of the defect itself. The assertion budget went to 20,000 ms and is the one term still not derived from a measurement, which the site says.
- **Still ungated, stated here rather than left implicit.** The margin reporter sees per-*test* budgets. It cannot see a `{ timeout: 30_000 }` on a single wait inside a browser spec, and `test-timeout.test.ts`'s literal scan does not read `tests/browser/**` at all. Roughly twenty-five such literals exist, all below that file's own 45,000 ms allowance — including the two this change raised from 5,000 to 30,000, which are *still* under the floor they were raised to satisfy. Two of the seven defects above were exactly this shape. Closing it means either extending the literal scan into the browser specs and raising every site, or deriving those waits from the allowance; neither was done here, and the next expiry in that class will not be caught by anything added in this change.
- The `Node 24 complete` job's own `timeout-minutes` went from 30 to 60. Its Windows leg finished in 29m28s while *abandoning* four tests early; a green run does strictly more work than a red one, so that budget was already the next failure.
- The fleet canon now says a push is finished when the remote gate says so, not when the remote accepts it, and that a red remote gate is the next task ahead of whatever was planned.

**What this register should be read for.** All of them were invisible to a green local run, and the two that were not timeouts were assertions about wall-clock latency written on a fast machine. A gate that only its author's hardware can satisfy is not a gate, and this repo had one lane where that was true for five weeks without anyone noticing.
