# Devlog — 2026-08-28

One session, spent entirely on a lane nobody had been reading. The owner asked for GitHub CI to be fixed, and then said the thing worth recording above any of the fixes: "You need to proactively monitor these things instead of hearing about it from me."

## `main` had not seen a green CI run in five weeks, and the local gate could not have known

The first count written into these notes said thirteen days, taken from the ten runs `gh run list` prints by default. It was wrong, and it was wrong in the direction that flatters: the last **successful** run on `main` was **2026-07-24**, and every push since — **131 runs, 100 failures and 31 cancelled** — was red. Nothing green in five weeks. The correction cost six documents, a canon line, and a re-sync of twenty-two repositories, all because a number was written from the first screen of output instead of from a query that answered the question asked.

The streak is not one defect and this entry does not claim it is. It spans a workflow matrix change (early-August runs failed a `Node 22 complete` job that no longer exists) and at least one unrelated cause — 2026-08-08 also failed `npm audit`. What was diagnosed is the state of the five most recent runs, 2026-08-18 through 2026-08-28, which fail identically. The four newest failed everywhere on one TypeScript error; behind it, the `Node 24 complete` job — the only job that runs `npm run verify` end to end, and therefore the only job that runs the browser suite — failed on both Linux and Windows.

The reason none of it was caught locally is the whole point of the entry. Every one of the browser failures is a wall-clock or budget failure that a fast machine cannot reproduce. CI rasterises in software on a shared runner and runs this suite 1.2x to 2.4x slower than the workstation these tests were written on, so the failing half of the matrix is the half the author's machine can never run. That multiplier is modest, which turns out to matter: the tests that broke were not far from breaking here. `npm run verify` was green before those pushes, and each one was green for a true reason and red for a true reason at the same time.

## Five defects, and only one of them was a bug in the product's sense

**The typecheck error** (`playground-joint-overlay.test.ts:86`, from `39a4d75`) passed a `LiveBodySnapshotV1` to `playgroundPrismaticCoordinateV1`, which declared `PlaygroundBodySnapshotV1` — a type carrying `principalInertia` and `principalInertiaFrame` for the energy verdicts. The function reads translation and rotation and nothing else, and the file's own header says its checks "hold identically over either lane's frames". The type contradicted the comment. Both coordinate functions now take a `PlaygroundBodyPoseV1` — translation and quaternion — which both lanes' snapshots satisfy structurally. Not a public API change: the package publishes `dist/**` and exports `core`/`physics`/`meshing`/`three`/`testing`, none of which reach `tools/studio`.

**The chain settled to an absolute tick without pausing first.** A live scene free-runs on the wall clock from the moment its solver is ready, so the tick it has reached when a test arrives measures how slow the machine is, not the scene. CI arrived to find 54 ticks already spent against a target of 30, and `settleSteps` runs forward only. Machine Works and the windmill already open with `setSceneAnimation(false)`, which makes `LivePhysicsSessionV1.create` build the world already paused (`studio-live-interact.ts:345`); the chain never adopted the idiom. It does now, and `settleLive(0)` after the world exists pins it. **The baselines did not move** — `git status` shows no change under `tests/browser/baselines/`, so reaching tick 30 by thirty pure steps produces the same pixels as reaching it by free-run-then-settle, which is the determinism the scene claims.

The comment above that settle had also been wrong in an interesting way. It said tick 30 was chosen because "a tick it is certain to have passed is reachable, and tick zero is not" — reasoning about the lower bound, while the code's guard is an upper bound. The failure was in the direction the comment did not consider.

**A latency budget wearing an invariant's clothes.** `model-studio-lighting-preference.spec.ts:280` asserted the scene clock advanced under 200 ms across a resume, meaning to prove that resuming does not credit the player with the time it spent paused. What it measured was its own round trip to the page: CI read 541.9 ms from a player that was behaving correctly. The invariant is already proved exactly, against an injected clock, in `player.test.ts` — held at 400 ms across a 19,600 ms pause, reading 500 ms a hundred milliseconds after the resume. The browser assertion was a racier duplicate of a unit test — but deleting it outright, which is what happened first, left the keyboard path with no bound at all, and review said so. It has a real one now: a capture-phase `keydown` listener stamps `performance.now()` when the page sees the key, and the advance is asserted to fit inside the page's own elapsed time since that stamp. The technique was already in the same file, at `:389-404`, for the button path.

**Two budgets that were never derived from anything.** `machine-works:612` wanted more than the flat 60-second test timeout, and `riverfall:445` could not capture a screenshot inside Playwright's unstated 5-second assertion default. The often-quoted 71.3 s (Windows) and 68.5 s (Linux) for the first are *not* its cost: the test was killed at sixty and those figures include unwinding and writing a failure trace. Measured alone on this workstation it is **53.0 s** — see below, because that number is the most useful thing this session produced.

## The gate that should have existed, and the carve-out that let it not

This repo bought the general lesson on 2026-08-07, when fifteen tests expired on a documentation-only diff: `tests/testing/test-timeout.ts` sizes every vitest budget as a fixed 45,000 ms contention allowance plus four times measured work, and `test-timeout.test.ts` scans every test file for a budget below that allowance — because "an explicit budget below the allowance is worse than no budget at all: it opts its test out of the floor every other test gets."

That scan skips `tests/browser/**`, on the stated grounds that Playwright specs have "their own gate and their own timeout config". They had neither. The browser lane carried a flat 60,000 ms nobody had measured against, plus a 5,000 ms assertion default that is precisely the unstated-default-below-the-allowance shape the 2026-08-07 entry describes. The carve-out was written as an observation about where responsibility lay, and it turned out to be the place responsibility was not.

**What the failure looked like before it was a failure** is why the new check watches margins rather than outcomes — and finding that out required measuring rather than reading a log.

The first version of this entry said `model-studio-windmill-assets.spec.ts:279` "passed on Windows in 60.0 s against its 60 s budget", which was a good story and false: that test declares `test.setTimeout(180_000)` at its own site, so 60.0 s was a third of its budget, not all of it. The number came from timestamps in a CI log, and a log does not say what a test was allowed.

Running the suite with the new reporter says it. `model-studio-machine-works.spec.ts:612` takes **53.0 s alone on this workstation, of the 60 s the lane gave every test — 88%**. It was never a fast test that a slow runner broke; it had seven seconds of room on the machine it was written on, and any host slower than that one was going to spend them. Had the reporter existed, the local run before the first red push would have said so. That is the whole argument for watching margins: the margin is visible on the machine where the failure is not.

`tests/testing/browser-timeout-headroom.ts` fails a *passing* run when any test has spent more than 75% of its budget, and prints the five closest to the edge on every run, green ones included.

It was confirmed to bite before it was believed: with the threshold neutralized to 0.0001, a two-test run reporting "2 passed" exited 1 with the offenders named. The first attempt at that confirmation reported `EXIT=0` and was itself wrong — the exit code had been read through a `| tail -8`, so it was `tail`'s status and not Playwright's. That is the never-pipe-a-verification-gate mistake, reproduced while in the middle of proving something else. `onEnd` also has to return a promise: Playwright declares it `Promise<{ status }> | void`, so the obvious synchronous `return { status: 'failed' }` neither typechecks nor changes the run's status.

The suite default is **119,900 ms**: the slowest test that actually uses the default (`riverfall:247`, 19.9 s measured alone here), plus the 45-second allowance `test-timeout.ts` charges for a machine that is not the author's, plus a 55-second margin for what a slow host does to the work on top of that — the 1.2x, 1.4x and 2.4x stretches measured between this machine and GitHub's Linux runner.

The two heavy tests do not use the default. `windmill-assets:279` already declared `test.setTimeout(180_000)` at its own site, and `machine-works:612` now does too, with its 53.0 s beside it. That is the shape a budget should have: sized for the test it guards, so the margin gate can say something true about each one. A single default stretched to fit the heaviest member is a budget for nothing else.

There is no `process.env.CI` branch anywhere in the file, deliberately. The defect was that the gate running locally was not the gate running on CI; a budget that only exists on CI is another instance of that, unexecuted locally and unasserted anywhere.

## What the critic found, including the one thing it was wrong about

The independent review landed several findings, and two of them were structural.

**The headroom gate could not detect the defect it was built for.** Raising the budget to 285,000 ms moved the gate's trip point to 213.75 s, at which every number in its own justification reads healthy — the whole point of the gate is that `machine-works:612` was at 88% of its budget, and under 285,000 that same 53.0 s reads as 19%. The gate would have sat silent until a test took three and a half minutes. The neutralization proof showed the plumbing worked, not that anything could ever cross the line.

The error underneath was double-counting, which `test-timeout.ts` warns about in as many words: "a number taken under load already has the contention allowance baked into it and double-counts". Its four-times multiple exists to scale a *workstation* measurement up to what a bad machine does to it; the 60.0 s was already taken on the bad machine, so multiplying it again bought a budget nothing could reach. The allowance alone is the right term to add to a figure measured on the slow host, which gives 105,000, and 120,000 with cover for the one test whose cost is still unknown. The gate's trip point is 90 s against a worst known passing measurement of 60 s — 50% headroom, and a line something can actually cross.

**The Riverfall diagnosis was challenged and the challenge was tested.** The critic argued the capture was not slow but never stable: `settleTo` pauses the solver and not the scene transport, the three kelp strands keep swaying, and `toHaveScreenshot` needs two consecutive identical frames. Every other capture spec in the suite pauses first; Riverfall was the only one that did not, and Riverfall was the one that timed out. A good argument, and wrong. Switching the simulation off before the captures produced a **visibly different picture** — 3,786 pixels on the unlit view — and looking at the two images says why: with the transport stopped the studio stops applying the live presentation's poses, and all 96 foam flecks snap back from the plunge pool to the lattice of their authored placements. The river's foam is *placed by the running frame loop*. It cannot be photographed still by stopping it, the canvas after `settleTo` is already static except for that, and the Windows failure was slowness after all. Reverted; the assertion budget stands as the fix.

That is worth keeping for its shape rather than its conclusion. Both the critic's reasoning and the author's original reasoning were plausible; the thing that settled it was rendering both and looking at them, and the answer was visible in one glance at the second image.

**A deleted assertion came back stronger.** The critic pointed out that `player.test.ts` proves `StudioPlayer` re-anchors when handed a correct `nowMs`, and nothing about the studio handing it one, or about Space reaching that path — so deleting the browser bound left the keyboard path unbounded. It also pointed at `:389-404` in the same spec, which measures an in-page `performance.now()` window around the resume and asserts the advance fits inside it. The Space path now uses that technique: a capture-phase `keydown` listener stamps when the page saw the key, and the advance is bounded by the page's own elapsed time since. That is a real bound, on the real path, that no round trip can inflate.

Confirmed to bite, on the second attempt. The first neutralization seeked the player forward to fake a catch-up, and the test failed — on `playing` two assertions earlier, because `harness.seek` also pauses. A fault that trips a different assertion proves nothing about the one under test. The second forced the elapsed window to zero instead, and the bound failed exactly where it should, `Received: 99.8` against `Expected: <= 2` — which also says the advance it measures is a real positive quantity rather than a rounding artifact that would satisfy any bound.

Also fixed from the review: the claim that renderer cost is "gated where it is actually measured" was false — `benchmark:scenes` is a manual lane in neither `verify` nor CI, and the browser test timeout was in fact the only thing watching Machine Works at 71.3 s, so the comment asserting otherwise is gone. `livePhysics().running` means the world *exists*, not that it is advancing, which the chain's new wait now leans on; both the harness type and the test say so. A doc line describing what each lane's snapshot carries had the contrast wrong.

## One more of the same, found by sweeping rather than by failing

`model-studio-riverfall.spec.ts:182` and `:186` carried explicit `{ timeout: 5_000 }` overrides on the waits for the live world to build and to start stepping. They had never failed — on Linux the pair completes in 2,520.7 ms — and the first instinct was to record them and leave them, since re-tuning a passing guard on speculation is how a guard stops guarding.

What settles it is not speculation but an inconsistency inside the one file: `mountRiverfall` allows **30 s** for that exact condition on that exact scene, and the other test allowed **5 s**. One of those two numbers is wrong regardless of what CI does, and the smaller one was also below the lane's own assertion budget — an explicit budget under the floor, which is the shape the 2026-08-07 entry names as worse than no budget at all. Both are 30 s now, matching the file's own precedent.

Worth noting for the next sweep: the reasoning that nearly left them was "Linux completes in 2.5 s, that is half the budget." Windows is the slower leg on every other number in this session — 71.3 against 68.5, and the 60.0 s windmill capture was Windows. Quoting the faster leg to justify a tight budget is the same mistake one paragraph after naming it.

## The job's own budget was already the next failure

`Node 24 complete` on Windows ran 29m28s against `timeout-minutes: 30` — while abandoning four browser tests early. A green run does strictly more work than a red one, so that job was going to start timing out as soon as the tests were fixed, and the fix would have looked like it had caused it. Raised to 60.

## Steering

The rule the owner's sentence deserves is now fleet canon, propagated to all 23 repos: a push is finished when the remote gate says so, not when the remote accepts it — watch the run to a conclusion, read its status at session start, and treat a red remote gate as the next task ahead of whatever was planned.
