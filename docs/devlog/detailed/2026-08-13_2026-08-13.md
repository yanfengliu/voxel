# Devlog — 2026-08-13

A full-codebase adversarial review across six lenses, run because the session opened on a state report and found the supply-chain gate red. Eight defects confirmed and fixed, six of them in `src/` and reachable from the public API; a ninth was confirmed, attempted, and reverted when the fix broke a working scene. The day's shape: **every finding that mattered came from a reviewer that executed something** — a probe, a grep against the installed dependency, a read of Three's own upload path — and the three findings this session nearly got wrong were the ones where a test was written to a claim rather than to observed behaviour.

## Three tests passed on unfixed code before they were made to bite

The rule says neutralize the fix and watch the test fail. Three tests this session needed it, each for a different reason, and none of the three failures would have been visible without the check.

The instance-upload test failed the rule twice over. First version: the batch carried no animation lane, so `animate()` hit `if (entry.animatedIndices.length === 0) continue;` and never reached the code under test — a green test proving nothing. Second version added a real animation lane and still passed, because the entry's `fullUploadPending` was still `true` from its own creation, and that branch legitimately clears ranges to request a whole-buffer upload. The data was not lost in that sequence; it went to the GPU the expensive way. Only the third version reproduced the defect, and it needed the actual production frame order: reconcile *and* animate in frame one to consume the pending full upload, then reconcile and animate again in frame two.

That is worth carrying: **the sequence that exposes a frame-loop bug is the sequence the frame loop actually runs**, and an abbreviated one can be masked by a state the first frame leaves behind.

The delta-side iterator test and the soft-CCD parity test both passed on first write, and both were confirmed by neutralizing the fix — though the soft-CCD one was later removed with the change it guarded (below). The iterator one would have been a genuine false pass — `Array.from` and an indexed copy behave identically on an ordinary array, so nothing about the test's *shape* guaranteed it was reaching the hostile path.

## `Array.from` is not bounded by the length you just checked

Both public validators did this:

```ts
if (value.length > maximum) fail(limitCode, path, limitMessage);
return Array.from(value);
```

`Array.from` consults `Symbol.iterator` before the array-like path. A caller's iterator is under no obligation to agree with `length`. A probe — control snapshot validating first, so the probe proved something — got **10,000 iterator yields out of an array declaring `length: 0`**, against `maxResources: 1`. A generator that never returns hangs `acceptSnapshot` synchronously on the caller's own thread, inside the function whose entire job is to bound untrusted input.

The fix is four lines. What is worth remembering is the shape: a bound checked against one property, and the value then read through a mechanism that consults a different one. The repo already had tests for oversized *declared* lengths (`render-delta.test.ts:767`) — the bound was tested, the copy was not.

## A message with no identity is not a stale message

`meshWorkerProtocolErrorV1` deliberately carries no `identity.jobId`: it answers a request the worker could not trust enough to echo. The scheduler's receipt path resolves a job id, gets `null`, and falls into `jobId !== job.activeJobId` — the stale-result branch, which counts the metric, discards the payload, and does *not* settle the slot, because a stale result by definition belongs to some other job that will settle itself.

Except this one is the active job's only reply. Nothing else is coming. There is no timeout anywhere in `src/` — grep-confirmed, zero hits for `timeout`, `watchdog`, `deadline` — so the slot stays busy for the life of the scheduler, `pump()` skips it forever, and after enough skew every worker is wedged. The visible symptom is a mesh pipeline that stops with no failed group, no error, and a `staleResults` counter that reads like ordinary churn.

Two halves of the same defect: the hang, and the diagnostic thrown away. The worker had already named the cause (`worker.unsupported-mesher`, with a path) and the scheduler discarded it. The fix settles the slot *and* carries the issue back through a new optional field.

## Two lanes that promise to be one world, and the obvious fix that broke a machine

`fixtures/physics-playground/playground-world.ts` sets `setSoftCcdPrediction(0.25)` on every dynamic body. `tools/studio/live-physics.ts` sets it only when a body plan declares it, and no playground profile ever declared it — `softCcdPrediction` appeared nowhere in the repository outside its own type declaration and the conditional that reads it. Rapier's default is 0.

Both files carry a comment promising the lanes are identical. `solver-rate.ts` records the measured difference: the falling-station drop buries **0.16427 m without soft CCD and 0.00342 m with it**. The studio user watched the deep burial; every headless check saw the shallow one.

So far this reads as a clean fix, and it was made: declare it in the profile builder, add a parity test, done. Then the full gate failed one browser spec — **the fired trebuchet knocked zero bricks down, where it had knocked 23 past a quarter metre.** Reverting that single line and rerunning the spec restored it, which settles the cause.

The headless trebuchet's 19 scenarios stayed green throughout, because **none of them assert the wall coming down**. The knock-down exists only in the browser lane.

That is what makes this hard rather than tedious. "Make the live lane match the twin" quietly assumes the twin is right. The twin is the lane with the assertions; the browser is the lane with a working machine. Soft CCD is a solver accuracy knob, not one of this universe's laws — and this repo has already measured that it reads linear velocity only and does nothing for a rotating contact. Nothing available says which lane should move.

Bending the browser expectation down to 0 bricks would have been the workaround-as-furniture the owner rule names. The change was reverted and the divergence recorded at its site with the measurement and the failed attempt, so the next session starts past this rather than at it.

**The general form:** when two lanes disagree, finding the difference is the easy half. The hard half is establishing which one is correct, and a parity fix that assumes an answer can silently break the lane that was right.

## The duplication was not a smell, it was the cause

`deleteStudioScene`'s open-scene branch was a hand-maintained copy of `closeSceneMode`'s teardown. It had drifted by exactly two calls — `liveInteract.openScene(null, …)` and `playgroundPanel?.sceneOpened(null)` — and those two are the ones that stop a live scene's Rapier world.

Nearly every shipped scene has a live profile now, and a live scene opens in Interact by default. So deleting the open scene left a solver stepping against a retired snapshot, pushing poses at instances that no longer existed, until `buildScenePoseDeltaV1` threw `pose.instance-missing` and painted an error over the model view the delete had just restored — with the Adjust/Interact buttons and the playground panel still visible, and `rebuild()` able to resurrect the deleted scene's world from `#lastOpen`.

A reviewer named the duplication as the cause rather than as an aesthetic complaint, and it was right: the two blocks were identical when written, and only one of them was updated when live physics arrived.

## A stale comment that told the next reader not to fix something

`physics-playground-materials.ts` carried twenty lines explaining that the playground had *not* reached the shared 60 Hz rate, that deriving the constant had been tried three times and backed out, and that the station thresholds and law damping rates were all measured at 240 Hz and needed re-measuring "before this constant can move."

The next line was `export const PLAYGROUND_TIMESTEP_S_V1 = SOLVER_TIMESTEP_SECONDS_V1;` — the derivation, already done.

This is worse than an out-of-date fact. It was a **standing instruction not to touch something, addressed to a reader who would have had no reason to doubt it**, sitting directly above the evidence that it was wrong. The rate scan strips comments by design, so no gate could ever catch it. The twin claimed a `1/240` tick in two more places.

## What the typecheck was not checking

`tsconfig.json` names fixture directories individually, because the compatibility consumers deliberately compile against a `dist` that does not exist during an ordinary typecheck. That list had drifted: `fixtures/chain-consumer` — four files, a live Rapier lane — and `fixtures/deterministic-math.test.ts` were in no TypeScript program at all. Vitest runs tests with types stripped and `eslint.config.js` disables type-aware rules for `fixtures/**`, so a wrong shape passed `typecheck`, `lint`, and `test` alike.

Adding them found three real `Object is possibly 'undefined'` errors immediately, from a `size.map(...)` that widened a tuple to `number[]`.

The gate written for it asks **the compiler** which files it covers, via `tsc --listFilesOnly`. The first version compared against the include list and produced four false positives, because TypeScript also pulls in whatever an included file imports. An include-list check answers a different question than the one that matters.

## Smaller things, recorded so they are not rediscovered

- The solver-rate scan listed `scripts/` among its scanned directories and filtered to `.ts`. Every file in `scripts/` is `.mjs`, so that directory contributed zero files while the scan's own comment claimed there was "nowhere left to keep a rate of one's own."
- The timeout meta-scan's trailing-argument regex required `)` immediately after the number, so the multi-line `},\n  600_000,\n);` form — already in the tree — was invisible to the gate whose promise is that no test opts itself out.
- CI ran the complete gate on Node 22 while `.nvmrc` and the canon declare Node 24 the baseline. The browser suite, compatibility, package and supply-chain gates never ran on the declared toolchain. Roles swapped.
- `voxel/physics` shipped after the frozen 1.0 tag, under version `1.0.0`, with no changelog entry. Packing HEAD produced a materially different public API under the same version as the immutable artifact.
- The `nanoid` advisory that opened the session was never reachable here: the vulnerable `customRandom` lives in nanoid's *secure* entry, and postcss imports `nanoid/non-secure`, which is **byte-identical between 3.3.16 and 3.3.18**. The bump was still correct — the gate blocks on `high` by design — but the exposure was nil, and only diffing both tarballs showed that.

## Still open

Eight findings were confirmed and deliberately left, each recorded in the review thread with its location and reasoning. The two most likely to bite next: `ChunkIndexV1`'s slot map grows without bound within an epoch and is fully copied on every build (a streaming-world concern, and nothing streams yet), and the chunk-overlap sweep sorts on `x` only, so a world one chunk thick in x does n²/2 comparisons and **rejects a valid snapshot** at around 1,415 chunks.

Eight browser specs still have no `pageerror` guard, including the Interact-lane spec that drives real pointer input against the whole app — the repo asserts page errors as a first-class check in nine other specs.
